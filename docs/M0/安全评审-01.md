## 2. P0-02（认证/角色/租户隔离）意见明细

### 2.1 五角色权限模型

- **P0-B 前置约束**: 权限矩阵必须落成两张正交表，不能揉在一个 role 字段里：
  - `role`（能力面）: owner/rep/clerk/warehouse/customer，接口守卫用；
  - `data_scope`（行范围）: ALL / SELF / OWN_CUSTOMERS / SELF_ORDER。依据=需求§2 矩阵语义（业务员"查自己绩效"、客户"查自己订单"、老板"查全部"是数据范围差异，不是角色差异）。
- **P1-1 客户是外部身份，必须与员工身份信道分离**: 三端两类主体（c 端微信登录 vs 内勤账密），JWT 须带 `aud`/`scope` 声明：客户 token 调内勤接口一律 403，反之亦然。否则"审单预检"等接口被越权调用是资损级。
- **P1-2 双重身份**: 老板可能同为大客户经理（用户地图 §7.1），一人多角色时 token 只签一个活动身份，切换须重签，禁止一个 token 同时带两顶帽子。
- **P1-3 账号禁用即时生效（阻断 B1 展开）**: 推荐 `user.token_version` 字段 + Redis/JWT 校验时比对（禁用/改密/角色变更即 bump），或 5 分钟内过期的短令牌+刷新条。**评审通过标准**：禁用账号后 ≤1 个请求周期内旧 token 失效，有对应用例。
- **P2-2 仓配/内勤边界**: 盘点"仓管盘、内勤核对"分工未冻结（需求 §8-Q11），P0-02 先按两角色分立实现，合并比拆分开销大。

### 2.2 租户隔离

- **阻断 B5**: 任务书 §4 Q12 默认假设"多租户字段第一天进表（已按此设计）"——确认此决策为硬约束：所有业务表 `tenant_id NOT NULL` + 复合索引首列。禁止"单商户先上、SaaS 化再补"，补租户的迁移成本在 P0-01 建 schema 时一次决策。
- **P1-4 Prisma 中间件单防线不够**: 应用层注入 tenant_id 属"君子协定"，忘写 where 即全租户泄漏。要求双层：① Prisma `$extends`/client 中间件强制注入；② PostgreSQL Row Level Security 以 `SET app.tenant_id` 兜底（直连 SQL 也拦）。验收必须含一条"绕过 ORM 裸 SQL 查他租户=空集"用例（P0-02 验收 ≥2 异常用例之一）。
- **P1-5 客户行的归属隔离**: 客户下单接口对 customer_id 一律取自 token，禁止信任请求体传入的 customer_id（防横向越权改他人订单/查他人账单）。

## 3. P0-03（审计与状态机）意见明细

### 3.1 审计表与不可变流水

- **阻断 B2 展开**: 
  1. `audit_log` 表对应用 DB 账号仅授 `INSERT, SELECT`（撤 UPDATE/DELETE/TRUNCATE）；
  2. 每日锚点哈希链：每行存 `prev_row_hash`（或批末 hash 表 + PG `pgcrypto`），内部人直接改库也能被检测；
  3. 记录内容 = 人 + 时间 + IP/渠道 + 单据 + **动作前后值**（改价前价→后价），对齐任务书 P0-T03"可按人/时间/单据追溯"。
- **红线动作清单（P0-T03 枚举补全，验收按此抽查）**: 改价执行(F7 落点)、信用拦截放行/特批(R2)、收款销账(F9)、抹零/坏账审批(§D7)、盘点差异调账(P1-T07)、退货数量变更(R4 只能多不能少——减少方向请求必须 4xx 留痕)、拒收/改单状态回滚(F2 异常)、期初迁移批改(P0-T13)。
- **幂等键（P0-03 要求③）**: 涉及资金/库存的写接口（收款、销账、出库、特批放行、一键调价生效）必须携带客户端生成的 `Idempotency-Key`，服务端唯一索引兜底；重试/双击不双写。此为拆单验收项，无则退回。

### 3.2 状态机

- **P0-C 统一状态机**: 订单(待确认→已确认→出库→配送→签收→销账/取消/拒收)、出库单、应收、收款四类，转换表集中定义（enum + 白名单转换），业务路由禁止裸 `UPDATE status`。非法转换返回 409 并留审计。
- **阻断 B4 展开**: 库存、应收余额一律为**投影**（由批次库存流水/应收流水推导 + 物化加速），流水表 append-only；每日对账 job 校验投影=流水重放，不一致告警（接运维闭环）。验收加一条：任意时点余额可从流水重放重建。
- **未签收不可销账（P0-T23）**: 是状态机白名单转换，不是业务代码 if——防止绕行路径。

### 3.3 订单价格快照不可篡改（本单点名项）

- **快照字段清单（P0-T11 落地要求）**: OrderLine 落单瞬间固化——成交价、价级来源（五级价哪级/一客一价/特单价）、触发该价的促销/返利参数（随单赠、开瓶费两态 R6）、价格记录版本号 `price_version`。调价后历史订单金额不变 = 快照读路径与价格主数据**物理脱钩**。
- **阻断 B3 展开**: OrderLine 金额/单价列在应用层设"写一次"守卫（Prisma middleware 拦截已落单行的 UPDATE amount/price），改价唯一合法路径=作废重开或红字冲销单（新单据、关联原单、全审计）。否则"哪个店该补货、返利核算"（S1/P1-T08）全部建立在可被篡改的数字上。
- **P1-8 备份与恢复（§4.2 末条落地核查）**: 计划书要求"每日全量备份 + DB 时间点恢复(PITR)"——P0-01 建 PG 时即开启 WAL 归档（仅有全量备份无 PITR = 两点间数据丢失窗口），并把"从备份恢复到指定时间点"列入上线前演练项；审计表 append-only 与哈希链锚点须随备份一并可恢复校验。
- **P1-6 签收凭证 = 争议最终事实（R9）**: 电子网签记录（客户签名图/时间/设备）同样纳入 append-only 范围，签收后回包装回填走增量单据不改原签收行。
- **P1-7 电子单据 6 个月（R8/P0-T32）**: "归档后客户不可见、后台可审计恢复" = **软归档**，禁止物理删除（酒类台账有追溯需要，删除即毁证）。实现为归档标志+客户查询路径过滤，非 drop。

## 4. 二次确认 + 审计红线核查（任务范围③, 对计划书 §2.3 红线5）

计划书 §2.3 红线5 原文:「任何影响库存、应收、价格的动作必须显示结果摘要、二次确认并保留审计记录」。逐动作核查如下（按"资损半径"要求二次确认=复核弹窗+强制审计，部分需第二人）：

| 动作 | 依据 | 安全要求 |
|---|---|---|
| 信用超额放行特批 | R2 资金命门 | 老板本人密码/人脸级再确认，留痕含放行金额+理由（P0） |
| 抹零/坏账审批 | §D7 | 审批+留痕已有条款，补"单笔上限+月累计上限"参数（P1） |
| 一键调价生效(F7) | 联动存货增减值 R7 | 预览差异清单→确认→审计（P1） |
| 销账冲正 | F9 | 只准红字新单，禁改原收款（并入 B3 原则）（P0） |
| 退货数量改少(R4 反向) | 只能多不能少 | 服务端硬拒 + 留痕尝试（P1） |
| 期初批量覆盖(P0-T13) | 差异清零才切 | 迁移窗口后锁死期初接口（P1） |

## 5. 结论与流转

- **对 P0-02**: 设计方向成立（Prisma 中间件+五角色），但 **B1/B5 + P1-1/P1-4 四项必须在开工前写进任务书验收条款**，否则"越权用例全绿"无法在裸 SQL 绕过和即时禁用两个场景下成立。
